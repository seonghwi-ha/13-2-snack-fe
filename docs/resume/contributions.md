## 2. 주요 작업 상세

### 2-1. 공용 메뉴 컴포넌트 (#35, #47, #53, #71)

- 카테고리 사이드 메뉴(`SideMenu`), 소분류 항목(`SubCategoryItem`), 탭(`TabMenu`), 메뉴 항목(`MenuItem`)을 `src/components/ui`에 공용으로 만들었다.
- 리뷰를 반영해 메뉴 데이터를 상수 파일로 분리하고, 아이콘(`ChevronIcon`, `XIcon`)을 컴포넌트로 추출했다.
- 이후 상품 리스트의 카테고리 사이드바가 이 컴포넌트를 그대로 쓴다 (#77).
- 팀 컨벤션 문서에 TypeScript 타입 선언 규칙을 추가했다 (#37).

### 2-2. 상품 리스트·상세와 API 연결 (#77, #81, #97)

- 상품 리스트는 TanStack Query `useInfiniteQuery` + `IntersectionObserver`로 무한 스크롤을 구현했다.
  다음 페이지 여부는 백엔드가 내려주는 `hasNext`로 판단한다 (백엔드도 직접 설계).
- 카테고리는 "대분류만 고르면 그 아래 전체, 소분류를 고르면 그 소분류만" 불러오도록
  `parentCategoryId` / `categoryId`를 나눠 보낸다.
- 등록·수정은 하나의 모달 컨테이너로 처리하고, 수정·삭제 메뉴는 등록자 본인(`isMine`)이나 관리자에게만 보여준다.
  `GET /me`가 id를 주지 않아 본인 여부를 알 수 없던 문제를, 백엔드 상세 응답에 `isMine`을 추가해 풀었다.
- 상품 상세에서 장바구니 담기를 연결했다.

### 2-3. 찜 기능 연결 (#121)

**문제**: 위시리스트 API와 `WishlistProvider`는 있었지만 상품 화면만 연결이 빠져 있어, 하트를 눌러도 서버에 저장되지 않았다.

**구현**

- 리스트 카드와 상세에 찜 상태·토글을 연결했다. 찜은 Provider가 낙관적으로 반영하고 실패하면 되돌린다.
- 공용 `ProductDetail`의 찜 상태를 내부 state에서 props로 바꿨다. 서버가 원본인데 컴포넌트가 따로 들고 있으면 새로고침이나 실패 때 어긋난다.
- 찜 개수가 바뀔 때 목록을 통째로 다시 받으면 스크롤과 페이지가 흔들리므로, 캐시의 숫자만 1 올리거나 내린다.

**트러블슈팅**

1. **하트가 이미지 아래로 밀려나는 문제**
   - 원인: 카드 전체를 덮는 링크(z-10) 위로 하트를 올리려고 `relative z-20`을 줬더니, `tailwind-merge`가 카드의 `absolute`를 같은 position 그룹으로 보고 지웠다.
   - 해결: position은 건드리지 않고 `z-20`만 넘겼다.
2. **정렬 드롭다운을 눌러도 카드가 눌리는 문제**
   - 원인: 펼친 정렬 목록과 카드 덮개 링크가 같은 `z-10`이라, 뒤에 그려지는 카드 링크가 클릭을 가져갔다.
   - 해결: 정렬 목록을 `z-30`으로 올렸다.

### 2-4. 상품 화면 성능·안정화 (#141, #158)

**첫 화면 표시 속도 (LCP)**

- 문제: 목록을 브라우저에서만 받으면 JS 다운로드 → 실행 → API 호출이 끝나야 `<img>`가 생겨, 느린 회선에서 LCP가 5초 넘게 밀렸다.
- 해결: 첫 페이지를 서버 컴포넌트에서 받아 `HydrationBoundary`로 넘겼다. HTML이 도착하자마자 이미지 요청이 시작된다.
  - 서버에서는 브라우저용 `fetchClient`(상대 주소 `/api`, 브라우저 쿠키)를 쓸 수 없어서, 요청 쿠키를 그대로 실어 API 서버를 직접 부른다.
  - API가 느려도 페이지 전체가 묶이지 않게 3초 타임아웃을 두고, 실패하면 `null`을 돌려 기존처럼 브라우저에서 받는다.
    액세스 토큰 만료도 여기 해당해서, 재발급은 브라우저의 `fetchClient`가 맡는다.
  - 서버와 화면의 쿼리 키가 한 글자라도 다르면 미리 받은 데이터를 쓰지 못하므로, URL → 조회 조건 변환을 `productListQuery.ts` 한 곳에 모았다.
- 첫 화면에 보이는 상단 이미지에만 `priority`를 줬다. `next/image`는 기본이 lazy라 이미 보이는 이미지도 늦게 받는다.

**오류 처리**

- `/products/abc`처럼 숫자가 아닌 주소는 요청하지 않는다. 요청을 막기만 하면 `isPending`이 계속 true라 스켈레톤이 영원히 남아서, 따로 "잘못된 상품 주소입니다."를 보여준다.
- 404·403 같은 4xx는 다시 요청해도 결과가 같다. 기본값(3회 재시도)이면 확정된 오류를 보여주기까지 7초가량 걸려서 4xx는 재시도하지 않게 했다.
- 4xx는 서버 문구를, 5xx·네트워크 오류는 사용자용 안내를 보여주고, 그때만 "다시 시도" 버튼을 띄운다. 오류 화면에는 항상 "상품 목록으로" 길을 둔다.
- 상품 화면에 에러 경계(`error.tsx`)를 추가했다.

**트러블슈팅: 배포에서 성능 개선이 조용히 꺼져 있던 문제 (#158)**

- 원인: 서버 조회가 `NEXT_PUBLIC_API_URL`을 읽고 있었는데, 배포 환경에는 서버용 `API_URL`만 있었다.
  값이 없으면 에러 없이 브라우저 조회로 넘어가게 만들어 둔 탓에, 화면은 정상이고 성능 개선만 꺼져 있었다.
- 해결: `next.config`의 `/api` 프록시와 같은 `API_URL`을 읽도록 고치고, 값이 없으면 개선이 꺼진다는 점을 주석으로 남겼다.
  서버에서만 읽는 값이라 `NEXT_PUBLIC_`이 필요 없다.

### 2-5. 찜 목록 안정화 (#152)

- **찜 직후 목록에서 빠지는 문제**: 상품 리스트에서 하트를 누르고 바로 찜 목록으로 넘어오면, 찜 요청이 아직 서버에 가는 중이라 방금 찜한 상품이 빠졌다.
  찜 목록을 받기 전에 진행 중인 찜 요청이 끝나기를 기다리게 했다.
- **에러 문구**: 서버가 꺼져 프록시가 낸 500이나 네트워크 끊김은 `API request failed: 500`, `Failed to fetch` 같은 개발용 문구라,
  4xx만 서버 문구를 쓰고 나머지는 안내 문구로 바꿨다. 어느 단계에서 실패했든 첫 페이지부터 다시 받는 재시도를 추가했다.

### 2-6. 화면 디테일과 협업 (#100, #104, #106, #109, #126)

- **카테고리 상수 정합성 (#100)**: 프론트가 들고 있는 카테고리 id를 백엔드 시드의 고정 id에 맞췄다.
  백엔드에서 시드를 돌릴 때마다 카테고리 id가 바뀌던 문제를 함께 고쳐(백엔드 #45), 두 저장소가 같은 id를 쓴다.
- **장바구니 개수 갱신 (#106)**: 상품 상세에서 장바구니에 담아도 상단 GNB의 개수가 그대로였다. 담기 성공 시 장바구니 갱신 이벤트를 보내 GNB가 다시 세게 했다.
- **이미지 없는 상품 (#126)**: `opacity`를 카드 바깥에 걸어 배경까지 흐려지던 것을 `[&_img]:opacity-15`로 아이콘에만 걸었다.
- **입력 안내 (#126)**: 제품 링크 오류를 "올바른 URL 형식이 아닙니다"에서 "https://로 시작하는 전체 주소를 입력해주세요. 예: …"로 바꿨다.
- **머지 복구 (#104)**: 다른 브랜치 머지로 깨진 주문·장바구니 서비스와, 공용 Badge 타입 변경에 맞지 않던 사용처를 정리했다.
- **이미지 API와 `next/image` (#77)**: `next/image` 최적화는 Next 서버가 이미지를 대신 요청해서 브라우저 쿠키가 실리지 않는다.
  우리 이미지 API 주소(`/api/...`)만 최적화를 끄고 브라우저가 직접 받게 했다.

## 4. 포크 이후 추가 작업 (개인)

팀 프로젝트가 끝난 뒤 포크 저장소에서 백엔드 포크에 추가한 기능을 화면에 연결했다. (PR 번호는 포크 저장소 기준)

### 4-1. 상품 목록 커서 페이지네이션 · 검색 · 오타 추천 (포크 #3)

- 무한 스크롤 다음 묶음을 백엔드의 `nextCursor`로 요청한다. 응답에 커서가 없으면 기존 `page` 방식으로 동작해 백엔드 배포 순서와 상관없이 깨지지 않는다.
- 상품 목록에 검색창을 추가했다. 검색어는 URL(`keyword`)에 두어 새로고침·뒤로 가기에도 유지되고, 카테고리와 상관없이 전체 상품에서 찾는다.
- 검색 결과가 없으면 백엔드 `pg_trgm` 추천(`suggestions`)을 "혹시 이 상품을 찾으셨나요?"로 보여주고, 누르면 그 이름으로 다시 검색한다.
- 다음 페이지 판단·검색어 정리 로직을 순수 함수로 분리해 테스트 10개를 붙였다.
- 입력칸을 URL과 맞추려고 effect 안에서 state를 바꾸던 코드를 lint(`react-hooks/set-state-in-effect`)가 막아, 비제어 입력 + `key={keyword}`로 다시 그리게 바꿨다.

### 4-2. PR CI (포크 #3)

- `main`으로 가는 PR·푸시마다 lint → 라우트 타입 생성(`next typegen`) → 타입 검사 → Jest → 빌드를 GitHub Actions에서 돌린다.
- 타입 검사는 Next가 만드는 라우트 타입(`LayoutProps` 등)이 있어야 통과해서 `next typegen`을 먼저 실행한다.
- 빌드는 `/api` rewrite 주소가 필요해 호출하지 않는 자리 표시 `API_URL`을 넣었다.

### 4-3. 구매 요청 멱등성 키 (Idempotency-Key)

**문제**: 서버는 주문을 만들었는데 응답이 끊기면, 사용자는 실패로 알고 다시 누른다. 장바구니는 이미 비워져서 두 번째 요청은 "구매 요청에 실패했습니다."가 뜨고, 사용자는 주문이 됐는지 알 수 없다.

**구현**: 백엔드 포크에 만든 `Idempotency-Key`(같은 키의 재요청에 처음 성공 응답을 돌려줌)를 장바구니 구매 요청에 연결했다.

- 같은 내용(상품·수량·요청사항)으로 다시 보내면 같은 키를, 내용이 바뀌면 새 키를 쓴다. 성공하면 키를 버린다.
- 같은 키로 다시 보내도 안전한 실패만 자동 재시도한다: 응답을 못 받은 네트워크 오류, 처음 요청이 처리 중(409 `IDEMPOTENCY_IN_PROGRESS`), 5xx. 0.5초·1초 간격으로 최대 2번.
- 예산 초과 같은 업무 오류는 다시 보내도 결과가 같아 재시도하지 않는다.
- `crypto.randomUUID`는 https·localhost에서만 쓸 수 있어, 그 밖에서는 `crypto.getRandomValues`로 키를 만든다.

**검증**: 키 형식·재시도 판단 테스트 12개. 로컬 백엔드와 브라우저(Playwright)로 첫 요청을 서버까지 보낸 뒤 응답만 끊었더니, 같은 키로 한 번 더 보내 저장된 응답(`Idempotent-Replayed: true`)을 받고 주문은 1건, 화면은 "구매 요청이 완료되었습니다."로 끝났다.

**배운 점**: 멱등성 키는 서버만으로 끝나지 않는다. 클라이언트가 "언제 같은 키를 다시 쓰고, 언제 새 키를 만들지"를 정해야 재시도가 안전해진다.
